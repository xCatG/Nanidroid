# Native ghost state persistence — design addendum for review

Status: approved by the user on 2026-09-23 for the native persistence checkpoint, implemented through [the approved persistence plan](../plans/2026-09-23-native-state-persistence.md). This addendum extends the completed native milestone with the lifecycle and persistence requirements below. The [baseline](2026-09-22-nanidroid-baseline-spec.md) and [architecture](2026-09-22-blind-recreation-design.md) still govern scope; the [milestone-two plan](../plans/2026-09-23-native-engines.md) describes the current implementation.

## Intent and evidence

Native engine-written state should survive an orderly ghost switch or Back exit followed by reload, including a fresh app process. Preserve bytes the engine has already written if Android kills the process abruptly. No promise is made that every native engine, ghost script, or shutdown path saves pending in-memory changes.

The installed master path is `filesDir/ghost/<id>/ghost/master`. `BundledGhostRepository.ensureInstalled()` returns immediately if the bundled ghost directory exists; it does not recopy an existing installation. `NativeShioriHost` gives the one native owner a dedicated thread and an opaque lease. `GhostRuntime` currently waits for OnGhostChanging or OnClose dialogue, then calls native unload without OnDestroy. The bundled installer and runtime must continue using the same master directory across activations and process starts.

Read-only inspection of the copied `app/src/main/jni/**` found Satori's engine writes `satori_savedata.txt` or `.sat` on unload, and YAYA's engine writes `yaya_variable.cfg` or `.ays` on termination; both can ignore save failure. Kawari's engine supplies a KIS `save` primitive but does not universally invoke it at unload. Satori also saves outside unload, through explicit and timer-driven paths (`satori_EventOperation.cpp`, `satori_tool.cpp`), and YAYA exposes `SAVEVAR`, which the Earthquake Duo fixture's bundled framework calls periodically (`system/yaya_shiori3.dic`). A Kawari ghost must choose when to save and load. The LOBO fixture calls `SaveData` from OnDestroy and also from every OnMinuteChange (`dict/dict-event.kis`). It loads `profile\dict-savedata.txt` during engine startup from `kawarirc.kis`, and its OnInitialize also runs `SaveLoad`. `SaveData` writes `profile\dict-savedata.txt`; Kawari's `CanonicalPath` converts the backslash, so the target is `ghost/master/profile/dict-savedata.txt`. `TKawariEngine::SaveKawariDict` opens a plain `ofstream` and does not create directories, and the fixture ships no `profile/` directory, so every save fails with only a Kawari error-log line. The connected device now has a native-created `satori_savedata.txt` in Satori's master (44 files versus 43 original) and `yaya_variable.cfg` in YAYA's master (31 versus 30); LOBO has no extra filename (16 versus 16) even though OnMinuteChange has already requested saves, which matches the missing-directory failure. These are **existence-only** observations, not evidence that changed values are restored. No reload or fresh-process persistence test has passed yet. Evidence is limited to the copied native tree, current app code, and user-provided fixture data; no reference app code or history is used.

[UKADOC's event list](https://ssp.shillest.net/ukadoc/manual/list_shiori_event.html) specifies OnDestroy at shutdown and OnInitialize at startup as NOTIFY events. Its [SHIORI/3.0 specification](https://ssp.shillest.net/ukadoc/manual/spec_shiori3.html) distinguishes NOTIFY from GET: ordinary `Value` dialogue is ignored for NOTIFY. The current codec always emits GET, so merely sending `ShioriEvent("OnDestroy")` would not implement that protocol contract.

## Options and decision

| Option | Effect | Limit |
| --- | --- | --- |
| Keep unload only | Satori and YAYA may save on their engine termination with no new protocol work. | LOBO's OnDestroy `SaveData` is missed and its saves still fail without `profile/`; LOBO's OnInitialize `SaveLoad` and other ghosts' lifecycle hooks never run. |
| Send native OnDestroy as GET before unload | Smallest call-site change; some engines may run the handler. | Treats a shutdown notification as a dialogue request, can produce unwanted script, and deviates from UKADOC. Does not address LOBO's save directory or restore. |
| **Provide `profile/`, send OnInitialize and OnDestroy as NOTIFY** | Gives native ghosts their standard startup and shutdown hooks and the per-ghost directory hosts conventionally provide, without copying or interpreting their state. Satori/YAYA still perform unload saves. | Needs a narrow request-method capability in the codec/host and tests; changes boot event order for native ghosts; cannot detect every internal save failure. |

**Recommend the third option.** Before loading any native engine, create `ghost/master/profile/` if it is missing (never delete or clear it). If creation fails, that is an activation error before any JNI load, handled like any other failed activation. Immediately after a successful native load and before OnBoot or any other GET, send exactly one OnInitialize NOTIFY on the new lease and ignore any returned script. OnInitialize is a courtesy notification that this app has never sent before, and a ghost or engine may answer it with 400 or another status without being broken; log a status other than 200/204 and continue booting. Only a transport failure or unresolved/quarantined ownership during OnInitialize counts as a failed load for fallback purposes. For a native session's orderly switch, finish the outgoing OnGhostChanging dialogue, then send exactly one OnDestroy NOTIFY on its existing lease with no references, ignore any returned script, and only then unload. For Back, finish OnClose dialogue and use the same notification-before-unload sequence. The host must serialize notification and unload on its native thread; stale leases must never notify a new owner. The shutdown notification belongs only to Satori, Kawari, and YAYA sessions, not the built-in or unsupported Kotlin engines. Do not send it during Activity recreation, pause/resume, or a merely selected ghost. A close that interrupts an in-progress switch still gets at most one shutdown sequence for the outgoing owner. If load completes after its caller is cancelled and host cleanup unloads it before a runtime session exists, that cleanup is outside the orderly dialogue path and has no OnDestroy guarantee.

Use the actual `NOTIFY SHIORI/3.0` method for both events, with the existing sender, security, charset, and request framing. Keep all currently specified dialogue events as GET. Accept decoded 200 or 204 as notification completion, regardless of any returned `Value`; never enqueue that value or wait for playback. Any other status (400, 500, etc.) is logged even when transport returned normally; for OnDestroy it is also recorded as a cleanup error, and for OnInitialize it does not fail activation. Kawari always answers NOTIFY with 204 (`kawari_shiori.cpp`), and LOBO's `System.Callback.OnNOTIFY` falls back to its OnGET dispatch, so both OnInitialize and OnDestroy reach its handlers. OnInitialize is included for lifecycle compatibility: ghosts may run startup work there, as LOBO's `SaveLoad` does, even though LOBO's restore does not depend on it alone. Per [UKADOC](https://ssp.shillest.net/ukadoc/manual/list_shiori_event.html#OnDestroy), both notifications carry `Reference0: reload` only for a ghost reload and otherwise have it absent or empty; this app has no reload, so both are sent without references. Send OnInitialize only for Satori, Kawari, and YAYA sessions, once per load, not on Activity recreation or resume.

Do not add an app-side ghost state serializer or copy the master directory at unload. Native engines own their formats and paths. The installed master directory must remain writable and stable. Milestone-three import and any later reinstall/update must reject overwriting an existing ghost by default or explicitly preserve its engine-written state files; an archive extraction must not replace the live master tree or erase save data. Design that update operation when it is introduced, using this preservation requirement.

## Failure behavior and limits

- If OnDestroy returns a status other than 200 or 204, or its transport throws, record a cleanup error. During a switch, show it on the stage. During Back the Activity is finishing, so log it and let Back finish; never block exit to display it. No persisted next-launch error notice is kept: the log and, where applicable, the host's quarantine are the record. If the lease is still known and the host is not quarantined, attempt the normal unload once and retain the error even if unload succeeds. Keep the host's existing quarantine rule; never issue another JNI call to an uncertain owner. Continue with the existing bundled fallback where a switch can recover. Do not present an orderly save as successful.
- Native calls have no timeout today, and a hung OnDestroy handler must not trap the user. Bound the orderly shutdown sequence (OnDestroy plus unload) with a fixed limit, for example five seconds, recorded in the implementation plan. The host's unload runs `NonCancellable` on the native thread, so wrapping it in `withTimeout` does not guarantee that Back finishes. The contract: the runtime stops waiting independently of the native call; at the deadline the host is quarantined, and quarantine stays permanent for the process even if the native call later returns; a late completion cannot publish success, clear the error, release the lease, or start another native operation. Then record the cleanup error and let Back finish or the switch fall back as it would after any other unresolved native failure.
- A successful NOTIFY response or successful JNI unload proves only that those calls returned. Satori/YAYA can silently fail to write, and a ghost's OnDestroy handler can omit or fail its own save. The app cannot offer a universal durability or atomicity guarantee. It should not fabricate a success indication for save completion.
- Abrupt process death, force stop, OS kill, crash, or power loss need not deliver OnClose, OnGhostChanging, OnDestroy, or unload. Files already written to the app-private master should remain available to a later process, subject to ordinary filesystem behavior; pending in-memory state may be lost. App uninstall, clear data, and future destructive updates are outside this guarantee.
- On Android the common exit is Home followed by a later silent process kill, not Back. A background kill loses changes made since the last engine- or ghost-triggered save: Satori's explicit or timer saves, YAYA `SAVEVAR` calls from the ghost's framework, LOBO's OnMinuteChange `SaveData` once `profile/` exists, or an orderly unload. How much is lost depends on each ghost's save frequency. This addendum accepts that limit; a save point when the app goes to the background (for example an unload/reload cycle at `onStop`) is a separate product decision and is not part of this change.

## Verification required before claiming persistence

Use data-only copies of the three user-provided fixtures on a disposable API 31+ device; do not commit fixture payloads. For **each** engine, choose a fixture operation with a known, observable value change and a way to read that value after reload. Record the initial value, make one controlled change, and verify both the expected real file bytes or content in that fixture's `ghost/master` and the restored value from a freshly loaded engine. Repeat through (1) orderly switch away and back, (2) Back exit and fresh app process. Compare only engine-owned files and hash/record the before and after bytes. A file's mere existence, timestamp, or native 200 reply does not establish restored state.

Satori: exercise a persistent variable or word, inspect `satori_savedata.txt` or `.sat`, and query the changed value after each reload. YAYA: exercise a persistent variable, inspect `yaya_variable.cfg` or `.ays`, and query its restored value. Kawari/LOBO: change a value in its `savedataParam` list (for example `username` or `talkinterval`), confirm `ghost/master/profile/dict-savedata.txt` contains it after OnDestroy (and after an OnMinuteChange), then verify the value after reload (restored by `kawarirc.kis` at startup, with OnInitialize's `SaveLoad` also run); do not infer success from a file count.

Rotation (2elf/Satori): recreating the Activity must not touch the native lifecycle. Set a recognizable conversation flag, rotate, and verify the same native owner/lease remains, no load, unload, OnInitialize, OnDestroy, or OnBoot repeats, and the flag still affects the next response. If a fixture offers no controllable observable value, document that engine as unverified and use a separate lawful data-only fixture or a minimal test ghost without adding a broad compatibility claim.

Focused protocol/runtime tests should assert exact GET/NOTIFY bytes; `profile/` created before load and never cleared, with creation failure reported as an activation error before any JNI load; OnInitialize once after load and before OnBoot; OnDestroy once and in order after dialogue/before unload; neither notification on recreation, resume, or for Kotlin engines; and no returned-script playback. Test decoded 200/204 acceptance and decoded 400/500/other-status errors, including the recorded error plus one unload for a still-known lease, and OnInitialize 400/500/other statuses logged while boot continues; separately test transport failure, the shutdown time limit with a permanently blocked native call (Back still finishes, quarantine) and with a call that returns after the deadline (quarantine stays, no success published, no further native operation), and quarantine without unsafe JNI retries. A separate abrupt-kill device test should first establish an already-written value and its file bytes, kill the app without orderly shutdown, then restart and verify those bytes and value remain; it should also record that no shutdown event was delivered and make no claim about an unsaved newer value. Preserve logs, fixture provenance, file hashes, and device/API/ABI with the milestone evidence. These tests are future implementation gates, not results of this review-only addendum.
