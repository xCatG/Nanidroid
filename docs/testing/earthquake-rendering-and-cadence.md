## Missing parts and bounded rendering fix

The original active stage drew only `surface0.png` for Mantle and `surface10.png` for Ridge. Those base images omit Mantle's default side arms and Ridge's eyes, mouth, eyebrows and crossed arms. The verified archive's `shell/master/surfaces.txt` assigns `always` layers to those surfaces: Mantle's 1501 `interpolate` and 1601 `overlay`; Ridge's 1101, 1001, 1403 and 1201 overlays. The referenced PNGs exist. The initial screen showed the omissions; the after screen showed Ridge's eyes/crossed arms and Mantle's side arms. The separately staged private instrumentation test checked that the composed images differ from the bases by more than 100 pixels for both characters.

Commit `08933a0` added parsing and static composition for supported `always` `overlay`/`interpolate` patterns, in declaration order, with signed-offset clipping and existing image alpha handling. Stage composition is keyed to surface files and loader, so a text-only update does not reload the layers. Commit `1663072` rejects a companion `.pna` path that escapes the shell through a symlink. Review follow-ups `1fe5789`, `3670388`, and `1e510be` use the stage's surface map instead of rescanning it for each surface load, move file checks to IO, preserve cancellation, fall back to base images when `surfaces.txt` is unreadable, reject a missing base, support selector lists/ranges/exclusions, and share numbered surface PNG matching. Only a single pattern 0 per `always` animation ID is flattened; since `14a6f70` its wait (a number or SSP `min-max` range) no longer matters, because a lone frame redraws itself unchanged. Dynamic multi-frame animation is skipped rather than stacked and remains milestone-four work. `element` composition and other methods remain outside this focused subset; composition clips to base bitmap bounds.

## Dialogue cadence

The first-boot passage had no authored wait or speed tag in the measured span. The old runtime delayed a nominal 50 ms, then advanced playback by a fixed 50 ms even when the callback arrived late. A probe measured 33 newly visible characters over 10.669 s, or **3.1 characters/s**. Commit `8e277b5` advances playback by nonnegative monotonic elapsed time, while resetting the baseline across pause/resume and preserving the existing clock-event callback schedule. After that change, timestamped text samples showed 131 characters over 6.7 s, or **19.6 characters/s**, near the nominal **20/s** rule. The samples establish average progress, not frame smoothness.

Independent review then found that a reply starting between callbacks could consume time from before that new script existed. Commit `eccf158` starts each new `ScriptPlayer` at its own monotonic timestamp. The focused replacement-dialogue regression failed against the prior commit and passed with the fix. That timing follow-up's full JVM report recorded **121 tests total, 2 skipped, zero failures**. Later commits `aacb733`, `728bf18`, and `7522d85` schedule `OnSecondChange` and `OnMinuteChange` from elapsed active-session time, coalesce delayed requests by event ID, and scope pending events to each ghost session. The persistence minute test directly invoked `OnMinuteChange`, so it did not validate runtime cadence. The earlier API 37 dialogue and frame measurements were not repeated for these clock changes. The known `\w8` script-semantic gap was outside this work.

## Remaining frame behavior

The initial emulator session also had a launcher ANR and severe host/device stalls, so its long-frame attribution was superseded after a cold boot without data wipe. On the recovered emulator, a 10-second ordinary Earthquake passage had **184/195 modern janky frames**, median **17 ms**, p95 **34 ms**, and 152 slow UI-thread frames. The separate launcher gesture window had 21/81 modern janky frames, median 18 ms. The app-associated jank therefore remained visible after the unhealthy system session ended, although the workloads are different and their percentages do not identify a cause.

A later bounded CPU profile replayed the same passage on the recovered emulator, with saved app-private boot state restored afterward. It measured **186/210 modern janky frames (88.57%)**, median **17 ms**, p95 **34 ms**, 174 slow UI-thread frames and 18 slow draw-issue frames. This profile was captured after stage loading; it does not establish that stage scanning caused per-character jank. `simpleperf` captured 339 CPU-clock samples with zero lost. Inclusive app-process samples included Compose frame dispatch (28.61%), recomposition/apply changes (27.73%) and remeasure/relayout (12.39%); these nested percentages must not be added. Samples for text measurement and scrolling were smaller, and no sorting hot spot was established. The profile shows distributed Compose UI work without proving one operation dominates the missed-frame critical path. No composite cache was added without measured benefit, since it would increase retained memory. A controlled single-variable comparison or frame trace is needed before selecting a further fix.

This evidence supports the identified static-part rendering repair and recovered average dialogue rate on the tested emulator. It does not establish smooth frames, full surface syntax, or full native compatibility.
